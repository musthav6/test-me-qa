# Тест-план Test-Me

## Об'єкт і мета

Test-Me (https://test-me.vzl.one/) — навчальний український інтернет-магазин: каталог із фільтрами, обране, порівняння, відгуки, кошик із промокодом і доставкою, оформлення та історія замовлень. Дані кожного клієнта живуть в окремому серверному середовищі (заголовок `X-Workspace-Token`, 24 години).

У застосунку є навмисні дефекти, тому очікувана поведінка береться лише з ТЗ, а не з того, як сайт працює зараз. Мета — перевірити ключові бізнес-правила і побудувати надійний набір UI- та API-автотестів.

**Документи:** [тест-кейси](test-cases.md) · [баг-репорти](bugs.md) · схема API https://test-me.vzl.one/openapi.json · звіт останнього прогону https://musthav6.github.io/test-me-qa/

## Стратегія

1. **Спершу дослідження, потім автоматизація.** Вісім ручних сесій за модулями: кошик, оформлення, замовлення, каталог, відгуки, обране й порівняння, середовище, адаптивність. Кожну перевірку проходили в UI і повторювали через API: так видно, де помиляється фронтенд, а де сервер. Результат — 11 дефектів у [bugs.md](bugs.md). Автотести писали вже під знайдені ризики.
2. **Більшість перевірок — на рівні API (88 тестів).** Розрахунок, валідація, статуси та ізоляція перевіряються через API: швидко, стабільно, не залежить від верстки. Граничні значення й класи еквівалентності — через `@pytest.mark.parametrize`, кожне значення окремим тестом.
3. **UI — лише те, що видно тільки в браузері (11 тестів, Selenium + Page Object).** Наскрізна покупка за зразком TM-CHECKOUT-001, подвійний клік, кошик і промокод після reload, повторне додавання товару, екранування HTML у відгуках, фільтр і пошук замовлень, покупка на 360px.
4. **Тест перевіряє ТЗ, а не поточну поведінку.** Якщо сайт порушує правило, тест чесно падає: без `xfail` і без підлаштування під баг. Червоний тест у звіті і є доказом розбіжності. Зв'язок «тест ↔ баг» ведеться в документації ([test-cases.md](test-cases.md), [bugs.md](bugs.md)), а не в коді.
5. **Очікуване не копіюється з відповіді сайту.** Суми рахує `helpers/pricing.py` за формулами ТЗ: цілі копійки, знижка 10% вниз до копійки, поріг доставки до знижки. Товари підбирає `helpers/catalog.py` за властивістю («у наявності», «залишок менше 10», «кошик рівно на 1 500 грн»), тож тести не прив'язані до id і цін.
6. **Кожен тест незалежний.** Тест створює власне середовище і не залежить від порядку запуску. Тому набір працює паралельно (`pytest -n 4`, pytest-xdist): у кожного worker'а свої token'и, як вимагає ТЗ.

## Пріоритети

Шкала та сама, що в тест-кейсах:

- **Високий** — гроші, основний сценарій покупки, безпека та ізоляція даних;
- **Середній** — важливі правила, які не блокують покупку;
- **Низький** — допоміжне.

|---|---|---|---|---|---|

## Нефункціональні перевірки (завдання з зірочкою)

| Тип | Що зроблено |
|---|---|
| Паралельні workers | `pytest -n 4`: кожен тест створює своє середовище; результат той самий, що й без паралельності |
| Перевірки API | 88 тестів по всіх ендпоінтах з ТЗ |
| Мобільний режим | TM-MOBILE-001: емуляція телефона 360 × 740 у Chrome |
| Нестабільність | Тести не залежать один від одного і від порядку; явні очікування замість `sleep`; на 429 клієнт чекає `Retry-After`. 10 повних прогонів      поспіль (-n 4): щоразу ті самі 10 падінь, 0 errors|
| Доступність | Перевірено вручну (сесія S8): підписи полів, навігація клавіатурою. Автоматизація (axe) — наступний крок |
| Мережеві помилки | Не автоматизовано. Наступний крок — відмова API через Chrome DevTools Protocol і перевірка видимого стану помилки |

## Поза покриттям

| Що | Чому |
|---|---|
| Округлення знижки до копійки | Усі ціни кратні 1 грн, тож 10% завжди дає цілі копійки. Без товару з «незручною» ціною округлення не перевірити |
| Завершення строку token (24 год) | Не дочекатись у межах прогону. Замість цього перевіряється 401 для невалідного token |
| Товари дорожчі за 100 000 грн | Фронтенд завжди надсилає `max_price=10000000` (ZN-11). Таких товарів зараз немає, тому це ризик, а не баг |
| Реальні платежі, листи, доставка | Їх немає в застосунку за ТЗ |
| Автоматизовано лише через API, в UI перевірено вручну | Пошук і фільтри каталогу, «Скинути фільтри» й перехід на сторінку 1, невідомий промокод і відхилена оплата в UI, обране (серце) |
| Лише вручну | «Почати заново», порівняння товарів, повторне замовлення, темна тема. Дефекти BUG-006 (прокрутка фону), BUG-007 (повідомлення з порівняння), BUG-011 (таблиця порівняння на 360px) знайдено вручну, автотестів на них немає |
| `servers` в openapi.json (BUG-001) | ТЗ не описує це поле і сам задає базову адресу; API за `/api` працює. Лишається ручною знахідкою |
| Інші браузери | Лише Chrome: стек ТЗ — Selenium, а Chrome є і локально, і в GitHub Actions |
| Навантаження | Rate limit 30 середовищ/хв і 180 записів/хв; навантажувати спільний публічний сайт неприпустимо |

## Ризики

| Ризик | Вплив | Як зменшуємо |
|---|---|---|
| Помилка в розрахунку (знижка, доставка, разом) | Клієнт платить неправильну суму | Високий пріоритет; граничні значення через API; незалежний оракул `pricing.py` |
| Подвійне замовлення | Подвійне списання коштів | UI-тест подвійного кліку з перевіркою кількості замовлень на сервері |
| Витік даних між середовищами | Чужі замовлення й відгуки | Окремий набір `test_isolation.py` |
| XSS у відгуках | Чужий код виконується в браузері покупця | UI-тест із HTML-вставкою і перевіркою, що скрипт не виконався, також після reload |
| Rate limit (429) | Нестабільні падіння при паралельному запуску | API-клієнт чекає `Retry-After`. Середовище для браузера створює API-клієнт, бо сам магазин на 429 не повторює запит |
| Спільний публічний сайт | Дані або ціни можуть змінитися | Товари підбираються за властивістю, очікування рахуються з каталогу; на відсутність потрібного товару тест стає `broken`, а не `failed` |
| Зміна верстки | Хибні падіння UI-тестів | Page Object: локатори лише в `pages/`, пріоритет `data-testid` → `id` → `data-*`, без XPath і текстів; явні очікування стану сторінки |
| Cloudflare блокує стандартний User-Agent Python (403) | Жоден API-тест не запуститься | Клієнт задає власний `User-Agent` |

## Середовище

- **Об'єкт:** лише опублікований сайт https://test-me.vzl.one/, як вимагає ТЗ (API 2.1.0, набір даних `test-me-v3`).
- **Стек:** Python 3.12+, pytest 8.3, requests 2.32, Selenium 4.25 (драйвер Chrome завантажує Selenium Manager), pytest-xdist 3.6, allure-pytest 2.13; звіт — Allure 3 (Node.js, без Java).
- **Браузер:** Google Chrome 1400 × 900, за замовчуванням без вікна; `--headed` — з вікном; для TM-MOBILE-001 — емуляція 360 × 740.
- **CI:** GitHub Actions на Ubuntu, запуск кнопкою (усі / API / UI); звіт публікується на GitHub Pages.
- **Дані:** токени створюються в тестах і не потрапляють у Git, скріншоти чи звіт; контактні дані вигадані.

## Робота з падіннями

Як запускати — у [README](../README.md). Якщо тест упав:

1. Відкрити тест у звіті Allure. Там є порівняння фактичного й очікуваного, а для UI — скріншот і URL сторінки в момент падіння.
2. Перевірити, чи це відома розбіжність із таблиці пріоритетів і [bugs.md](bugs.md). Якщо так — тест лишається червоним, доки сайт не виправлять.
3. Якщо падіння нове — відтворити вручну і перевірити тест. Якщо помиляється сайт, оформити баг-репорт зі скріншотом і запитом/відповіддю API; якщо помиляється тест, виправити тест.
