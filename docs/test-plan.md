# TM-QA: Test-Me, магазин — тест-план [IN REVIEW]

Статуси: DRAFT → IN REVIEW → BLOCKED / APPROVED.

## Вступ

Test-Me (https://test-me.vzl.one/) — навчальний український інтернет-магазин: каталог із фільтрами, обране, порівняння, відгуки, кошик із промокодом і доставкою, оформлення та історія замовлень. Дані кожного клієнта живуть в окремому серверному середовищі (token `X-Workspace-Token`, 24 години). У застосунку є навмисні дефекти, тому очікувана поведінка береться лише з ТЗ, а не з поточної реалізації. Мета: перевірити ключові бізнес-правила й побудувати надійний набір UI- та API-автотестів.

## Стратегія тестування

**1. Дослідницьке тестування (виконано).** Вісім сесій за модулями (кошик, оформлення, замовлення, каталог, відгуки, обране і порівняння, середовище, адаптивність). Кожна перевірка проводилась паралельно в UI та через DevTools → Network / Local Storage, щоб відрізнити помилку фронтенду від помилки API. Результат: 11 дефектів (BUG-001…011), див. [bugs.md](bugs.md).

**2. Піраміда автотестів: більшість перевірок на рівні API.**
- **API (~30 тестів, pytest + requests).** Бізнес-правила (розрахунок, валідація, статуси, ізоляція) перевіряються через API: це швидко, стабільно і не залежить від верстки. Граничні значення й класи еквівалентності параметризуються (`@pytest.mark.parametrize`).
- **UI (~12 тестів, Selenium + Page Object).** Лише те, що видно тільки в браузері: наскрізний сценарій покупки (TM-CHECKOUT-001), стан у localStorage після reload, повідомлення користувачу, захист від подвійного кліку, екранування HTML у відгуках, 360px.

**3. Незалежність тестів.** Кожен тест створює власне середовище (`POST /api/workspaces`) і не залежить від порядку запуску. Це також готує набір до паралельного запуску (pytest-xdist): кожен worker має свій token, як вимагає ТЗ.

**4. Відомі дефекти.** Тест перевіряє поведінку з ТЗ, а не фактичну. Якщо вона зламана, тест позначено `@pytest.mark.xfail(strict=True, reason="BUG-xxx: …")`. Звіт лишається зеленим, баг видно явно, а коли його виправлять, тест стане XPASS і впаде: це сигнал прибрати позначку.

**5. Оракул для грошей.** API повертає цілі копійки, UI показує гривні. Очікувані суми в тестах рахуються за формулою з ТЗ («разом = товари − знижка + доставка»), а не копіюються з відповіді.

### Поза покриттям

| Що | Чому |
|---|---|
| Округлення знижки до копійки | Усі ціни в наборі даних кратні 1 грн, 10% завжди дає цілі копійки. Перевірити округлення неможливо без товару з «незручною» ціною |

### Запуск і робота з падіннями

```bash
pytest -v              # весь набір
pytest -v -m api       # лише API
pytest -v -m ui        # лише UI (додати --headed, щоб бачити браузер)
pytest -n 4            # паралельно
```

Якщо тест падає: перевірити, чи є баг у [bugs.md](bugs.md). Якщо є — позначити тест `xfail` із BUG-ID. Якщо немає — відтворити вручну, оформити новий BUG-xxx зі скріншотом і запитом/відповіддю API.

## Ризики та залежності

### Ризики

| Ризик | Вплив | Як зменшуємо |
|---|---|---|
| Помилки розрахунку (знижка, доставка, разом) | Клієнт платить неправильну суму | P0, параметризовані API-тести на граничні значення; знайдено BUG-002, BUG-003 |
| Подвійне замовлення | Подвійне списання коштів | UI-тест подвійного кліку; API ідемпотентності не гарантує за ТЗ |
| Витік даних між середовищами | Чужі замовлення й відгуки | Окремий набір `test_isolation.py`, P0 |
| XSS у відгуках | Виконання чужого коду в браузері покупця | UI-тест із HTML-вставкою, P0 |
| Rate limit (429) | Нестабільні падіння при паралельному запуску | Клієнт повторює запит після `Retry-After` |
| Спільний публічний сайт | Дані або версія можуть змінитись без попередження | Тести створюють власні дані, не залежать від чужих; `GET /api/health` фіксує версію |
| Залежність UI-тестів від верстки | Хибні падіння після зміни дизайну | Page Object: локатори в одному місці; явні очікування замість `sleep` |
| Фронтенд обмежує ціну 100 000 грн (ZN-11) | Дорогі товари не показуватимуться в каталозі | Зафіксовано як ризик; зараз не баг |

### Залежності

- Доступність https://test-me.vzl.one/ і Cloudflare (403 для стандартного User-Agent Python)
- Chrome і chromedriver (Selenium Manager завантажує драйвер автоматично)
- Для CI: GitHub Actions, для звітів — Allure

## Оцінка впливу на автоматизацію

| Область | Примітки |
|---|---|
| Фреймворк | `api/client.py`: базова адреса, token, власний User-Agent, повтор на 429. Фікстури в `conftest.py`: `anon_api`, `api` (нове середовище на тест), `driver` |
| Ідентифікатори UI | У застосунку немає `data-testid`: локатори будуються за класами (`.product-card`) і текстом кнопок. Ризик крихкості, тому всі локатори в `pages/` |
| Інше | Стан браузера в localStorage `test-me:v2` (`token`, `cart`, `compare`): UI-тести можуть читати його для перевірок |
